Overview

Reoffending predictors has two related journeys on the same section. The static assessment collects offending history so the service can calculate static predictor scores. The dynamic assessment starts from an interview gate: if the practitioner has interviewed the person, they answer further questions (accommodation through risk of serious harm) for dynamic scores; if not, they continue to static check answers and scores only.

How the design evolved

This journey is an early step from OASys into HMPPS Assess and plan. We started from learnings on SAN (Strengths and Needs Assessment) about leading practitioners through a set of questions, and we are working to set the foundations of assessments for the ARNS Assess and plan platform.

  • Clarify questions and how they map to scores
  • Add guidance in context so practitioners are more likely to answer sexual offending questions correctly (wrong inputs are currently high)
  • Make clear what data comes from outside the service (for example NDelius), while showing that practitioners can trust the source
  • Make it easy to get scores, and to change them when new information is available
  • Incentivise practitioners to do an interview so they can get dynamic scores that give a more accurate picture of reoffending risks

Static journey at a glance

  1. 1 Offending history
  2. 2 Sexual offending
  3. 3 Community date
  4. 4 Offences since
  5. 5 Check answers
  6. 6 Predictor scores
Static journey steps as a list
  1. Offending history — always shown
  2. Sexual offending — shown if sexual or sexually motivated offending is yes; otherwise skipped
  3. Community date — always shown
  4. Offences since — shown once a complete community date is entered; almost always in this prototype
  5. Check answers — always shown
  6. Predictor scores — always shown; mark the section complete

Dynamic journey at a glance

  1. 1 Interview
  2. 2 Accommodation to RoSH
  3. 3 Drugs / alcohol detail
  4. 4 Check answers
  5. 5 Predictor scores
Dynamic journey steps as a list
  1. Interview (a6) — Yes continues to dynamic questions; No goes to static check answers (a7)
  2. Accommodation (b1) and employment (b2) — always on the Yes path
  3. Drug use (b3); drug detail (b4) only if misused drugs is yes
  4. Alcohol use (b5); alcohol detail (b6 or b6c) depending on timing of use
  5. Relationships (b7), thinking (b8), offence analysis (b9), risk of serious harm (b10)
  6. Check answers (b11) — static plus dynamic sections
  7. Predictor scores (a8) — dynamic origin; mark the section complete

User journey

There are two paths in the same section. The static path starts at Current offence and offending history (a2b) and never visits Interview (a6). The dynamic path starts at Interview (a6), with static answers seeded, and either continues through Accommodation to Risk of serious harm (b1–b11) or drops back to static Check your answers if there was no interview.

When static questions appear

Sexual offending questions
  • If yes to sexual or sexually motivated offending: show the sexual offending page and sexual scores later
  • If no: skip those questions and show sexual scores as not applicable
Offences since community date
  • Shown once a full community supervision start date has been entered
  • In this prototype a full date is almost always collected, so this page usually appears
Most recent offence date
  • Only asked if offences have happened since community supervision began
  • If the answer is changed to no, that date is removed
Changing an answer from Check your answers
  • Change takes the practitioner back to that question
  • After saving, they usually return to Check your answers
  • Exception: if the new answer means another page is now needed (for example changing sexual offending to yes)

When dynamic questions appear

Interview done
  • Yes → first incomplete dynamic page (usually Accommodation (b1))
  • No → static Check your answers (a7), then static scores on Predictor scores (a8)
  • Changing Yes → No from Check your answers (b11) pauses dynamic answers and returns to Check your answers (a7)
Drug detail (b4)
  • Shown only if “ever misused drugs” is yes on Drug use (b3)
  • Changing off yes clears stored drug detail
Alcohol detail (b6 / b6c)
  • Yes including last 3 months → Alcohol detail (b6) (frequency, units, binge)
  • Yes but not in last 3 months → Alcohol binge only (b6c)
  • No or Unknown → skip to Personal relationships (b7) and clear alcohol detail
Domestic abuse conditionals (b9)
  • Perpetrator yes reveals “against whom”
  • Changing off yes clears the follow-up
Relationship status Unknown
  • On Predictor scores (a8), ARP and VRP fall back to Static tags even when other predictors are Dynamic

Behaviours and patterns

How things behave

  • Errors: a3 (stranger victim) and b1 (living with) use a GOV.UK error summary plus field errors. Other pages may still focus the first missing field — live service should use a full error summary everywhere.
  • Extra questions: Answering yes can reveal a follow-up (for example, most recent offence date, drug detail, alcohol detail, domestic abuse against whom). Changing to no clears it.
  • Current offence: Shown from NDelius. If wrong, contact PDU — not editable here.
  • Change answer: Goes back to that question, then returns to Check your answers (a7 or b11).
  • Mark complete: Shows a success message, status becomes Complete, and the main button is hidden.
  • Return to OASys: Link is shown but not active in this prototype.
  • Unknown answers: Selecting 'Unknown' is usually treated the same as 'No' or null — it does not reveal follow-up questions or change the scoring path.

Dynamic-specific behaviours

  • Entry seeding: Starting dynamic from the index clears session, seeds current offence, then backfills static history so a6 can run without walking a2b–a5.
  • Interview gate: Yes opens the dynamic path; No goes to a7 for static scores.
  • Pause / restore: Interview Yes → No moves dynamic answers into pausedDynamicSection; Yes again restores them.
  • Two CYA pages: a7 is static-only; b11 includes static and dynamic sections and sets scores origin to b11.
  • Incomplete guards: a7 and b11 redirect to the first incomplete page before showing the summary.
  • Score tags: Dynamic origin shows Dynamic on predictors, except ARP and VRP when relationship status is Unknown (forced Static) — including after Change from b11.
  • Exclusive checkboxes: Alone / Unknown (living with — under “or”, mutually exclusive), Unknown (important people), and None of these patterns clear other selections.

Components used

  • PDS header
  • Primary navigation (MOJ)
  • Phase banner
  • Back link
  • Headings with captions
  • Radios (inline Yes/No; longer options on dynamic pages)
  • Checkboxes with exclusive “or” dividers on dynamic multi-selects
  • Date inputs (inputmode="numeric")
  • Narrow text inputs for counts (govuk-input--width-4)
  • Tables, details, inset text, warning text, section breaks
  • Summary lists with Change actions
  • Error summary (a3 stranger validation; b1 living with)
  • Tags (status, risk band, Static / Dynamic)
  • Notification banners (success; scores summary region)
  • Primary / secondary buttons
  • PDS footer

Accessibility

  • Visible question headings paired with visually hidden legends where needed
  • aria-describedby on dates, hints, and numeric fields
  • Date fieldsets use role="group"
  • Change links include visually hidden context
  • Status appears in H1 as visually hidden text; visible tag is aria-hidden
  • Score sections: role="region" + aria-labelledby
  • Focus management after mark complete and when using #top
  • b8 Help details: visually hidden question text after “Help to answer this question”

Design decisions baked into behaviour

  • Static entry: Static assessment starts at a2b — index “Static assessment” links there (design frozen 23 July 2026); a1 / a2 are out of path
  • Skip a6 on static: a5 continues to a7; no “continue to dynamic” question on the static journey or on a7 CYA
  • Dynamic entry: Index “Dynamic assessment” links to a6 with static answers seeded (design frozen 31 July 2026); uses the same /dev chrome
  • Interview incentive: a6 copy steers Yes toward dynamic scores and No toward static check answers
  • CYA edit loop: Change → edit → Save returns to a7 or b11 (including sexual yes → no, and interview yes → no which drops to a7)
  • Caption nesting: Caption is a <span> inside the H1 so screen readers announce both
  • Single-question pages: H1 / caption sit in the fieldset legend (a4 / a6 pattern)

  10. 10. Caption nesting and H1-as-legend Screen readers get caption + title together; single-question pages use the H1 as the legend.

UI components (1)

Shared visual language so practitioners recognise the same meaning across assessments.

UI component

Inset text (highlighted) — MOJ

Challenge
How to represent information that has been confirmed so users recognise ‘info from a source of truth’?
Design
MOJ inset text highlighted (grey vs blue).
How to use
  • Grey: subtle — small reminder / “to let you know”; changeable (for example last page, you did this); support and playback.
  • Blue: highlight — should not change; confirmed; summary; more focus and more contained (source of truth — solid piece of info).
Why ARNS-wide
ARNS pulls info from multiple places. Users should be confident that the key info we present is from a trusted source and they can confidently use it.
References
MOJ Design System — Inset text (highlighted)

Accessibility (5)

MOJ accessibility review recommendations and JS-off patterns that should be standard platform chrome.

A11y

JavaScript off — search fallback

Challenge
How do we ensure users have access to search functionality if their JS is turned off?
Design
A fallback solution for the JS-off case.
How to use
Use a search button that submits to a results page (GET form), instead of relying on client-side filtering alone.
Why ARNS-wide
Simple and accessible pattern that benefits every assessment that includes search.
References
Document with JS on / JS off screenshots and the search results page when available.
A11y

Age calculator — JS on vs JS off

Challenge
Different behaviours for the age calculator feature create inconsistency if each assessment invents its own fallback.
Design
One shared progressive-enhancement contract for age-from-date.
How to use
  • JS on: live age update (no button); use aria-live as the user types.
  • JS off: show a Calculate age button that updates age on submit/refresh.
Why ARNS-wide
Date-to-age appears in multiple assessments. Matching behaviour reduces cognitive load and keeps accessibility outcomes consistent.
References
Used on research proto date fields; not shown on the current static predictors path.
A11y · review item 1

Nest captions inside H1s

Challenge
Screen readers often miss the relationship between a section caption and the page title when they are separate elements.
Design
Nest the caption <span> inside the H1 so both are announced together.
How to use
<h1 class="govuk-heading-l">
  <span class="govuk-caption-l assessment-service-header__section-caption">Predictors</span>
  Accommodation
</h1>
Why ARNS-wide
Every assessment uses a section caption + page title. One pattern keeps navigation announcements predictable across services.
References
MOJ accessibility review item (1); applied on predictors service headers.
A11y · review item 3

Section landmarks for page structure

Challenge
Screen reader users need reliable ways to jump between chrome, person identity, and the main task without guessing heading levels.
Design
Use section landmarks in the page structure so screen reader users can better navigate.
How to use
Wrap offender / person identity in a <section> landmark labelled by the person name heading; keep the task H1 as the primary page heading.
Why ARNS-wide
Person identity appears on every assessment page. Shared landmarks make the platform feel like one product.
References
MOJ accessibility review item (3).
A11y

‘Offender details’ as a screen reader heading

Challenge
Without a clear landmark label, identity fields (CRN, PNC, DOB) are hard to find or understand in isolation.
Design
Expose ‘Offender details’ (or equivalent) as a heading / accessible name for the identity region.
How to use
Label the offender section landmark so assistive tech can announce it as a navigable region, while the visible person name remains the in-page heading.
Why ARNS-wide
Same identity chrome on all assessments; one naming and heading approach for screen reader users.
References
MOJ accessibility review recommendation.

Forms & conditionals (1)

Keep branching questions predictable and light wherever they appear.

Forms · review item 22

Keep conditional reveals simple

Challenge
Nested or multi-step conditional reveals increase cognitive load and make no-JS / a11y behaviour harder to maintain.
Design
If we need to show another question in a conditional reveal, it should be simple.
How to use
Prefer one clear follow-up question per reveal (for example Yes → date). Avoid stacking multiple nested reveals unless research shows a clear need.
Why ARNS-wide
Assessments share form patterns. Simple conditionals keep journeys scannable and reduce errors across services.
References
MOJ accessibility review item (22); mirrored in predictors offences-since reveal.
