Overview

The static assessment collects offending history and related answers so the service can calculate reoffending predictor scores. Practitioners move through a short question journey, check their answers, then view scores and mark the section complete.

How the design evolved

This journey is an early step from OASys into HMPPS Assess and plan. We started from learnings on SAN (Strengths and Needs Assessment) about leading practitioners through a set of questions, and we are working to set the foundations of assessments for the ARNS Assess and plan platform.

  • Clarify questions and how they map to scores
  • Add guidance in context so practitioners are more likely to answer sexual offending questions correctly (wrong inputs are currently high)
  • Make clear what data comes from outside the service (for example NDelius), while showing that practitioners can trust the source
  • Make it easy to get scores, and to change them when new information is available
  • Incentivise practitioners to do an interview so they can get dynamic scores that give a more accurate picture of reoffending risks

Journey at a glance

  1. 1 Offending history
  2. 2 Sexual offending
  3. 3 Community date
  4. 4 Offences since
  5. 5 Check answers
  6. 6 Predictor scores

Dashed steps are conditional. In the current prototype a complete community date almost always shows a5.

Journey steps as a list
  1. Offending history — always shown
  2. Sexual offending — shown if sexual or sexually motivated offending is yes; otherwise skipped
  3. Community date — always shown
  4. Offences since — shown once a complete community date is entered; almost always in this prototype
  5. Check answers — always shown
  6. Predictor scores — always shown; mark the section complete

When questions appear

Sexual offending questions
  • If yes to sexual or sexually motivated offending: show the sexual offending page and sexual scores later
  • If no: skip those questions and show sexual scores as not applicable
Offences since community date
  • Shown once a full community supervision start date has been entered
  • In this prototype a full date is almost always collected, so this page usually appears
Most recent offence date
  • Only asked if offences have happened since community supervision began
  • If the answer is changed to no, that date is removed
Changing an answer from Check your answers
  • Change takes the practitioner back to that question
  • After saving, they usually return to Check your answers
  • Exception: if the new answer means another page is now needed (for example changing sexual offending to yes)

Behaviours and patterns

How things behave

  • Errors: Prototype only focuses the first missing field. Live service should use a full error summary.
  • Extra questions: Answering yes can reveal a follow-up (for example, most recent offence date). Changing to no clears it.
  • Current offence: Shown from NDelius. If wrong, contact PDU — not editable here.
  • Change answer: Goes back to that question, then returns to Check your answers.
  • Mark complete: Shows a success message, status becomes Complete, and the main button is hidden.
  • Return to OASys: Link is shown but not active in this prototype.

Components used

  • PDS header
  • Primary navigation (MOJ)
  • Phase banner
  • Back link
  • Headings with captions
  • Radios (inline Yes/No)
  • Date inputs (inputmode="numeric")
  • Narrow text inputs for counts (govuk-input--width-4)
  • Tables, details, inset text, warning text, section breaks
  • Summary lists with Change actions
  • Tags (status, risk band, Static)
  • Notification banners (success; scores summary region)
  • Primary / secondary buttons
  • PDS footer

Accessibility

  • Visible question headings paired with visually hidden legends where needed
  • aria-describedby on dates, hints, and numeric fields
  • Date fieldsets use role="group"
  • Change links include visually hidden context
  • Status appears in H1 as visually hidden text; visible tag is aria-hidden
  • Score sections: role="region" + aria-labelledby
  • Focus management after mark complete and when using #top

Design decisions baked into behaviour

  • Entry: Static assessment starts at a2b — index “Static assessment” links there; a1 / a2 are out of path
  • Skip a6: a5 continues to a7; no “continue to dynamic” question on this journey or on CYA
  • CYA edit loop: Change → edit → Save returns to a7 (including sexual yes → no, which drops sexual sections)
  • Caption nesting: Caption is a <span> inside the H1 so screen readers announce both
  • Single-question pages: H1 / caption sit in the fieldset legend (a4 pattern)

UI components (1)

Shared visual language so practitioners recognise the same meaning across assessments.

UI component

Inset text (highlighted) — MOJ

Challenge
How to represent information that has been confirmed so users recognise ‘info from a source of truth’?
Design
MOJ inset text highlighted (grey vs blue).
How to use
  • Grey: subtle — small reminder / “to let you know”; changeable (for example last page, you did this); support and playback.
  • Blue: highlight — should not change; confirmed; summary; more focus and more contained (source of truth — solid piece of info).
Why ARNS-wide
ARNS pulls info from multiple places. Users should be confident that the key info we present is from a trusted source and they can confidently use it.
References
MOJ Design System — Inset text (highlighted)

Accessibility (5)

MOJ accessibility review recommendations and JS-off patterns that should be standard platform chrome.

A11y

JavaScript off — search fallback

Challenge
How do we ensure users have access to search functionality if their JS is turned off?
Design
A fallback solution for the JS-off case.
How to use
Use a search button that submits to a results page (GET form), instead of relying on client-side filtering alone.
Why ARNS-wide
Simple and accessible pattern that benefits every assessment that includes search.
References
Document with JS on / JS off screenshots and the search results page when available.
A11y

Age calculator — JS on vs JS off

Challenge
Different behaviours for the age calculator feature create inconsistency if each assessment invents its own fallback.
Design
One shared progressive-enhancement contract for age-from-date.
How to use
  • JS on: live age update (no button); use aria-live as the user types.
  • JS off: show a Calculate age button that updates age on submit/refresh.
Why ARNS-wide
Date-to-age appears in multiple assessments. Matching behaviour reduces cognitive load and keeps accessibility outcomes consistent.
References
Used on research proto date fields; not shown on the current static predictors path.
A11y · review item 1

Nest captions inside H1s

Challenge

Forms · review item 22

Keep conditional reveals simple

Challenge
Nested or multi-step conditional reveals increase cognitive load and make no-JS / a11y behaviour harder to maintain.
Design
If we need to show another question in a conditional reveal, it should be simple.
How to use
Prefer one clear follow-up question per reveal (for example Yes → date). Avoid stacking multiple nested reveals unless research shows a clear need.
Why ARNS-wide
Assessments share form patterns. Simple conditionals keep journeys scannable and reduce errors across services.
